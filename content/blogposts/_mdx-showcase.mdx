This post is a **living reference**: copy/paste any of the snippets below into other posts.

On blog and project pages, a **collapsible table of contents** is rendered automatically above the article (from `##`–`####` headings plus `<CitatiоnBox>` and `<MediaPresence>` section titles). You normally should **not** add a second `<Toc />` inside the MDX. Use `<Toc items={[…]} />` only when you need a fully manual list inside the body.

## Design language

- **Layout**: legacy-inspired blog cards, dashed borders, calm typography.
- **Dark mode**: everything should remain readable, with preserved hierarchy.
- **MDX blocks**: framed “content widgets” that don’t fight the article text.

## Prose examples: paragraphs and lists

  ### H3
  #### H4
  ##### H5
  ###### H6


  Plain paragraphs are the default: they inherit spacing and color from the article body. Use *emphasis*, **strong**, and `inline code` in the flow of a sentence.

  A second paragraph shows the usual gap between blocks. For the same underline style as MDX components, use a normal markdown link: [example.com](https://example.com).

  **Unordered list** (bullets, GFM):

  - First item with **bold** and a nested level:
    - Nested bullet one
    - Nested bullet two
  - Second top-level item
  - Third item with a [link inside the list](https://example.com)

  **Ordered list** (numbered):

  1. First step. Numbering is automatic.
  2. Second step; lines can wrap when the column is narrow, like this longer sentence that demonstrates wrapping in the article layout.
  3. Third step to finish the sequence.

  **Circled numbers** (no component; plain HTML in MDX). Same padding and spacing as other lists; markers are ①–⑳, then decimal if you go past 20:

  <ol class="mdx-list-circled">
    <li>Yet, it happened that under the current methodology, “interesting” buildings are often repetitive because of construction patterns (housing blocks, industrial sites, etc.).</li>
    <li>Some of the <em>actually most complex</em> structures are not mapped well and need case-by-case handling.</li>
  </ol>

  Mixed idea: after a list, another short paragraph resets the rhythm before the next heading.

## Optional collapsible section and paragraphs, blocks, lists, and carousels inside collapsibles

  <CollapsibleSection title="Optional collapsible section" level={3} defaultOpen={false}>
    Longer sections can live inside **`CollapsibleSection`**: native `<details>` behavior, with a real heading (`level` **2**, **3**, or **4**) for outline and ToC. The sidebar ToC picks up `title` and `level` from the opening tag, using the same slug as the rendered heading.

    - `defaultOpen={true}` starts expanded.
    - Default hints: **Click or tap to open/close section**; override with `hintOpen` / `hintClose` or hide with `showHint={false}`.
    - Omit duplicate markdown `###` with the same text, or you will get two ToC entries.  
  </CollapsibleSection>

  MDX mixes **markdown** and **JSX**. Block-level JSX (`<div>…</div>` split across lines) must sit in its own “paragraph” in the AST: put **blank lines** before the opening tag and after the closing tag. If you glue `<div>` to prose without a blank line, you can get compile errors like `Expected a closing tag for <div> … before the end of paragraph`. **Do not put `<div>` inside a markdown paragraph.** The renderer wraps prose in `<p>…</p>`, and `<p>` cannot contain `<div>`, which breaks HTML and can cause hydration errors like `Expected server HTML to contain a matching <div> in <p>`. For **inline** chips or highlights, use `<span style={{ display: 'inline-block', … }}>` (or plain `<span>`) instead; reserve `<div>` for blocks separated by blank lines.

  Long posts often put **several paragraphs**, **markdown lists**, **`<NavigatorGrid />`**, and **`<Carousel />`** in the same `<CollapsibleSection>`. Use a **blank line** between paragraphs, between a paragraph and a list, and **before and after** block JSX so MDX does not merge invalid nesting.

  Open the **parent** section below for copy-pasteable **`level={4}`** demos (all under one **`level={3}`** parent). Nested `<details>` is valid HTML.

## Under construction cover (WipReveal)

  Blog and project **detail** pages automatically wrap the article body in this cover when frontmatter has `wip: true`, or a `version` that looks like a draft (`draft`, `draft article`, `draft-beta`, …). Title and meta stay clear; click the frosted overlay once to peek. Set `wip: false` to opt out even if `version` mentions draft.

  You can also wrap **any block** in MDX (blank lines before and after the tags):

  <WipReveal title="Sample chart section still in progress">

    Pretend this is unfinished work: a short paragraph, a list, and a small image strip sit behind the cover until you click.

    - Blurred preview of the body
    - Kicker: **Under construction**
    - Hint: **Click to peek anyway**

    <Carousel
      caption="Placeholder media behind the WIP cover"
      items={[
        { src: "https://picsum.photos/1200/800?random=41", alt: "WIP demo 1" },
        { src: "https://picsum.photos/1200/800?random=42", alt: "WIP demo 2" }
      ]}
    />

  </WipReveal>

  Optional props: `kicker`, `title`, `hint`, and `active` (default `true`; use `active={false}` to render children with no cover).

## Optional Interactive footnotes

  Footnotes can show a preview popover on hover/focus and still work as normal jump links.<FootnoteRef id="1" /> In longer writing, they are useful for source links, caveats, and small side notes that would otherwise interrupt the paragraph rhythm.<FootnoteRef id="2" />

  Imagine you are describing a migration from legacy HTML to MDX: the main text can stay focused on decisions and outcomes, while footnotes hold implementation details, dates, and external references.<FootnoteRef id="3" /> This keeps the narrative readable on first pass, but still gives power users context one hover away.

  You can also use footnotes for "method notes" in data posts: sample size assumptions, API limits, and timing windows.<FootnoteRef id="4" /> In practice, readers who need those details can open them instantly, and readers who do not can keep moving without losing flow.

    </FootnoteDefinition>
