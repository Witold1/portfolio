On blog and project pages, a collapsible table of contents is rendered automatically above the article (from ##–#### headings plus <CitatiоnBox> and <MediaPresence> section titles). You normally should not add a second <Toc /> inside the MDX. Use <Toc items={[…]} /> only when you need a fully manual list inside the body.

Design language

  • Layout: legacy-inspired blog cards, dashed borders, calm typography.
  • Dark mode: everything should remain readable, with preserved hierarchy.
  • MDX blocks: framed “content widgets” that don’t fight the article text.

Optional collapsible section and paragraphs, blocks, lists, and carousels inside collapsibles

Optional collapsible section▾
Click or tap to open section

Longer sections can live inside CollapsibleSection: native <details> behavior, with a real heading (level 2, 3, or 4) for outline and ToC. The sidebar ToC picks up title and level from the opening tag, using the same slug as the rendered heading.

  • defaultOpen={true} starts expanded.
  • Default hints: Click or tap to open/close section; override with hintOpen / hintClose or hide with showHint={false}.
  • Omit duplicate markdown ### with the same text, or you will get two ToC entries.

MDX mixes markdown and JSX. Block-level JSX (<div>…</div> split across lines) must sit in its own “paragraph” in the AST: put blank lines before the opening tag and after the closing tag. If you glue <div> to prose without a blank line, you can get compile errors like Expected a closing tag for <div> … before the end of paragraph. Do not put <div> inside a markdown paragraph. The renderer wraps prose in <p>…</p>, and <p> cannot contain <div>, which breaks HTML and can cause hydration errors like Expected server HTML to contain a matching <div> in <p>. For inline chips or highlights, use <span style={{ display: 'inline-block', … }}> (or plain <span>) instead; reserve <div> for blocks separated by blank lines.

Long posts often put several paragraphs, markdown lists, <NavigatorGrid />, and <Carousel /> in the same <CollapsibleSection>. Use a blank line between paragraphs, between a paragraph and a list, and before and after block JSX so MDX does not merge invalid nesting.

Open the parent section below for copy-pasteable level={4} demos (all under one level={3} parent). Nested <details> is valid HTML.

NavigatorGrid nested inside a collapsible▾
Click or tap to open section

Short intro in markdown. Block components like <NavigatorGrid /> and <MediaGrid /> need the same blank-line discipline: isolate the grid from paragraphs above and below. The grid control defaults to Uniform (square tiles, like /gallery). Default imageFit is none for uniform tiles; use imageFit="cover" to match the gallery, imageFit="contain" to letterbox (e.g. maps), or set grid="variable" (or the toolbar) for masonry.

Optional Interactive footnotes

Footnotes can show a preview popover on hover/focus and still work as normal jump links.1 In longer writing, they are useful for source links, caveats, and small side notes that would otherwise interrupt the paragraph rhythm.2

Imagine you are describing a migration from legacy HTML to MDX: the main text can stay focused on decisions and outcomes, while footnotes hold implementation details, dates, and external references.3 This keeps the narrative readable on first pass, but still gives power users context one hover away.

You can also use footnotes for "method notes" in data posts: sample size assumptions, API limits, and timing windows.4 In practice, readers who need those details can open them instantly, and readers who do not can keep moving without losing flow.
